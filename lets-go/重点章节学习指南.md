## 一、先建立整体视图

一个请求在最终项目中的主要流向如下：

```text
客户端请求
    ↓
标准中间件：panic 恢复 → 请求日志 → 安全标头
    ↓
ServeMux：根据 HTTP 方法和 URL 选择路由
    ↓
动态中间件：会话加载 → CSRF 防护 → 身份识别
    ↓
受保护路由可再经过：授权检查
    ↓
Handler：解析和验证请求、调用模型、选择响应
    ↓
Model：执行 SQL、把数据库错误转换成领域错误
    ↓
数据库连接池
```

请优先理解这五个边界：

1. `http.Handler` 是所有 HTTP 组件的共同接口。
2. Handler 负责 HTTP；Model 负责数据访问。
3. Middleware 负责跨多个请求处理器的通用逻辑。
4. Session 保存跨请求状态；Request Context 只保存单次请求状态。
5. 接口和依赖注入让生产实现可以在测试中替换为模拟实现。

## 三、Chapter 2：Foundations

原文入口：[Chapter 2 Foundations](02.00-foundations.md)

### 1. Go Web 应用的核心抽象

`http.Handler` 接口只有一个方法：

```go
type Handler interface {
    ServeHTTP(ResponseWriter, *Request)
}
```

任何实现了 `ServeHTTP(http.ResponseWriter, *http.Request)` 的值都是 Handler。

普通处理函数本身不是 Handler，但 `http.HandlerFunc` 可以把它适配成 Handler：

```go
func home(w http.ResponseWriter, r *http.Request) {
    w.Write([]byte("Hello"))
}

var h http.Handler = http.HandlerFunc(home)
```

`http.ServeMux` 自身也实现了 `http.Handler`。因此整个应用可以理解为一串 Handler：服务器调用 ServeMux，ServeMux 再调用匹配的应用 Handler。

重点阅读：[http.Handler 接口](02.10-the-http-handler-interface.md)

### 2. 路由规则

Go 1.22+ 的标准 ServeMux 支持“方法 + 路径”模式：

```go
mux.HandleFunc("GET /{$}", app.home)
mux.HandleFunc("GET /snippet/view/{id}", app.snippetView)
mux.HandleFunc("POST /snippet/create", app.snippetCreatePost)
```

需要记住：

- `GET` 路由也会匹配 `HEAD`；其他方法要求精确匹配。
- 方法不匹配时，ServeMux 自动返回 `405 Method Not Allowed` 和 `Allow` 标头。
- `/{id}` 匹配一个非空路径段，通过 `r.PathValue("id")` 读取。
- URL 中的值全部是不可信输入，必须转换和验证。
- 以 `/` 结尾的是子树模式；若只想精确匹配根路径，应使用 `/{$}`。
- 重叠路由中“更具体”的模式优先；无法判断优先级的冲突模式会在注册时 panic。
- `/post/{path...}` 可以匹配剩余的全部路径段。

典型的路径参数处理：

```go
id, err := strconv.Atoi(r.PathValue("id"))
if err != nil || id < 1 {
    http.NotFound(w, r)
    return
}
```

重点阅读：[路由请求](02.03-routing-requests.md)、[通配符路由](02.04-wildcard-route-patterns.md)、[方法路由](02.05-method-based-routing.md)

### 3. HTTP 响应的顺序

响应通常按以下顺序构造：

1. 设置标头：`w.Header().Set(...)`
2. 写入状态码：`w.WriteHeader(status)`
3. 写入响应体：`w.Write(...)`

一旦调用 `WriteHeader()` 或首次调用 `Write()`，响应标头基本已经发送，之后再修改标头不会生效。若直接调用 `Write()`，默认状态码为 `200 OK`。

使用状态常量而不是魔法数字：

```go
w.WriteHeader(http.StatusCreated)
http.Error(w, http.StatusText(http.StatusInternalServerError), http.StatusInternalServerError)
```

重点阅读：[定制响应](02.06-customizing-responses.md)

### 4. 项目组织、模板和静态文件

本书逐步形成的职责划分：

```text
cmd/web/          Web 应用入口、路由、Handler、中间件
internal/models/  数据访问层
internal/...      仅当前模块内部可导入的辅助包
ui/html/          HTML 模板
ui/static/        CSS、JavaScript、图片
```

关键点：

- `go.mod` 定义模块路径和依赖版本。
- `internal` 目录由 Go 工具链强制限制外部导入。
- HTML 模板使用 `html/template`，它会按上下文自动转义动态数据。
- 模板继承通常由基础模板、局部模板和页面模板组成。
- 静态文件可通过 `http.FileServer` 提供，常与 `http.StripPrefix` 配合。

### 5. 并发意识

每个 HTTP 请求通常在独立 goroutine 中处理。因此：

- Handler 和中间件可能同时执行。
- 共享对象必须是并发安全的，或由锁/其他同步机制保护。
- 不要在请求间复用可变的局部状态。
- `sql.DB` 和 `slog.Logger` 可以安全地供多个 Handler 并发使用。

## 四、Chapter 3：Configuration and Error Handling

原文入口：[Chapter 3 Configuration and Error Handling](03.00-configuration-and-error-handling.md)

### 1. 运行时配置

不要把网络地址、DSN 等环境相关值散落在业务代码中。书中使用命令行标志：

```go
addr := flag.String("addr", ":4000", "HTTP network address")
dsn := flag.String("dsn", "web:pass@/snippetbox?parseTime=true", "MySQL DSN")
flag.Parse()
```

重要特性：

- 支持默认值。
- `flag.Parse()` 必须在读取值前调用。
- `flag.String()` 返回指针。
- `flag.Int()`、`flag.Bool()`、`flag.Duration()` 等负责类型转换。
- `-help` 自动生成配置说明。
- 可以用 `flag.StringVar()` 把配置集中到一个 `config` 结构体中。

环境变量可以在启动脚本中转换成命令行参数，从而同时保留环境注入与类型检查、默认值、帮助信息。

重点阅读：[管理配置设置](03.01-managing-configuration-settings.md)

### 2. 结构化日志

`log/slog` 的日志由以下部分组成：时间、级别、消息和属性。

```go
logger := slog.New(slog.NewTextHandler(os.Stdout, nil))
logger.Info("starting server", "addr", *addr)
logger.Error("request failed", "method", r.Method, "uri", r.URL.RequestURI())
```

核心原则：

- 使用稳定的消息和结构化属性，便于检索、聚合和告警。
- 开发环境可用文本格式；机器处理通常更适合 JSON Handler。
- 日志写到 `stdout`，让运行环境决定收集和保存位置。
- 不要把密码、会话令牌等秘密写入日志。
- `slog.Logger` 可并发使用。

重点阅读：[结构化日志](03.02-structured-logging.md)

### 3. `application` 结构体与依赖注入

把应用级依赖集中在一个结构体中：

```go
type application struct {
    logger   *slog.Logger
    snippets models.SnippetModelInterface
    users    models.UserModelInterface
}

func (app *application) home(w http.ResponseWriter, r *http.Request) {
    // 可以通过 app 使用依赖
}
```

它比全局变量更好，因为：

- 依赖是显式的。
- Handler 的可测试性更好。
- 测试时可以替换实现。
- 应用初始化集中在 `main()`。

这里的“依赖注入”并不需要框架，本质只是：由 `main()` 创建对象，再把对象交给需要它的组件。

重点阅读：[依赖注入](03.03-dependency-injection.md)

### 4. 集中错误处理

区分两类错误：

- 客户端错误：请求本身有问题，返回 `4xx`。
- 服务器错误：应用或依赖发生意外问题，记录内部细节，只向用户返回通用 `500`。

```go
func (app *application) serverError(w http.ResponseWriter, r *http.Request, err error) {
    app.logger.Error(err.Error(),
        "method", r.Method,
        "uri", r.URL.RequestURI())

    http.Error(w,
        http.StatusText(http.StatusInternalServerError),
        http.StatusInternalServerError)
}

func (app *application) clientError(w http.ResponseWriter, status int) {
    http.Error(w, http.StatusText(status), status)
}
```

不要把数据库错误、堆栈、文件路径等内部信息发送给客户端。需要调试的信息放进日志；对外响应保持最小化。

### 5. 隔离路由

```go
func (app *application) routes() http.Handler {
    mux := http.NewServeMux()
    // 注册路由
    return mux
}
```

这样 `main()` 只负责三件事：

1. 读取配置。
2. 创建依赖。
3. 启动服务器。

路由集中后，测试可以直接把 `app.routes()` 交给 `httptest.Server`，这是第 13 章端到端测试的重要基础。

## 五、Chapter 4：Database-driven Responses

原文入口：[Chapter 4 Database-driven Responses](04.00-database-driven-responses.md)

### 1. `database/sql`、驱动和连接池

`database/sql` 提供统一接口，数据库驱动负责具体协议。驱动常用空白导入注册：

```go
import _ "github.com/go-sql-driver/mysql"
```

```go
db, err := sql.Open("mysql", dsn)
```

最重要的认知：`*sql.DB` 是连接池，不是一条连接。

- `sql.Open()` 通常只初始化池，不保证已经连上数据库。
- 启动时用 `db.Ping()` 验证连接配置。
- 连接池应长期存活，在 `main()` 中创建并注入模型。
- 不要在每个 HTTP 请求里调用 `sql.Open()`。
- `sql.DB` 可安全并发使用。
- DSN 格式和特殊参数属于驱动约定，例如 MySQL 的 `parseTime=true`。

重点阅读：[创建数据库连接池](04.04-creating-a-database-connection-pool.md)

### 2. 数据访问层

将 SQL 封装在 Model 中：

```go
type SnippetModel struct {
    DB *sql.DB
}

func (m *SnippetModel) Insert(...) (int, error)
func (m *SnippetModel) Get(id int) (Snippet, error)
func (m *SnippetModel) Latest() ([]Snippet, error)
```

职责边界：

- Handler：HTTP 输入、验证、状态码、模板和重定向。
- Model：SQL、扫描结果、数据库错误转换。
- 数据结构：表示领域数据，例如 `Snippet`、`User`。

Handler 不应依赖 `sql.ErrNoRows` 之类的存储细节。Model 应将其转换成领域错误：

```go
var ErrNoRecord = errors.New("models: no matching record found")
```

```go
if errors.Is(err, sql.ErrNoRows) {
    return Snippet{}, ErrNoRecord
}
```

上层再把 `ErrNoRecord` 映射为 HTTP `404`。使用 `errors.Is()` 能正确处理经过包装的错误；检查错误类型时使用 `errors.As()`。

重点阅读：[设计数据库模型](04.05-designing-a-database-model.md)、[单记录查询](04.07-single-record-sql-queries.md)

### 3. 三种常用查询方法

| 方法 | 适用场景 | 典型返回值 |
| --- | --- | --- |
| `DB.Exec()` | `INSERT`、`UPDATE`、`DELETE` 等不返回结果集的语句 | `sql.Result` |
| `DB.QueryRow()` | 预期一行的查询 | `*sql.Row`，错误通常在 `Scan()` 时出现 |
| `DB.Query()` | 返回多行的查询 | `*sql.Rows` |

写入数据：

```go
result, err := m.DB.Exec(stmt, title, content, expires)
id, err := result.LastInsertId()
```

单行查询：

```go
err := m.DB.QueryRow(stmt, id).Scan(
    &s.ID, &s.Title, &s.Content, &s.Created, &s.Expires,
)
```

多行查询必须完整执行清理和错误检查：

```go
rows, err := m.DB.Query(stmt)
if err != nil {
    return nil, err
}
defer rows.Close()

for rows.Next() {
    var s Snippet
    if err := rows.Scan(&s.ID, &s.Title); err != nil {
        return nil, err
    }
    snippets = append(snippets, s)
}

if err := rows.Err(); err != nil {
    return nil, err
}
```

`rows.Close()` 很关键：未关闭的结果集会占用底层连接，最终耗尽连接池。

### 4. SQL 注入与占位符

永远不要用字符串拼接把不可信输入放进 SQL：

```go
// 正确：参数独立传递
_, err := db.Exec(
    "INSERT INTO snippets (title, content) VALUES (?, ?)",
    title,
    content,
)
```

占位符只用于数据值，不用于表名、列名或 SQL 关键字。不同数据库的占位符语法不同，例如 MySQL 使用 `?`，PostgreSQL 常用 `$1`。

### 5. 事务

连续调用两次 `DB.Exec()` 不保证使用同一连接，也不保证原子性。需要原子操作或固定连接时使用事务：

```go
tx, err := db.Begin()
if err != nil {
    return err
}
defer tx.Rollback()

if _, err = tx.Exec(...); err != nil {
    return err
}
if _, err = tx.Exec(...); err != nil {
    return err
}

return tx.Commit()
```

惯用模式是立即 `defer tx.Rollback()`：如果已经成功提交，之后的 Rollback 只是无操作；如果中途返回，则自动回滚。

必须确保每个事务最终执行 `Commit()` 或 `Rollback()`，否则连接无法及时归还连接池。

### 6. NULL 与 prepared statement

- 数据库 `NULL` 不能直接扫描进普通 `string`、`int` 等类型，可使用 `sql.NullString` 等可空类型。
- 如果业务允许，使用 `NOT NULL` 和合理默认值通常能简化 Go 代码。
- `Exec()`、`Query()` 和 `QueryRow()` 已经在内部安全地处理参数化语句。
- 长期复用 `DB.Prepare()` 可能提高某些高频复杂查询的性能，但会增加生命周期管理和连接池复杂度；先测量，再优化。

## 六、Chapter 6：Middleware

原文入口：[Chapter 6 Middleware](06.00-middleware.md)

### 1. 标准中间件模式

```go
func myMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // 调用下游之前执行
        next.ServeHTTP(w, r)
        // 下游返回后执行
    })
}
```

它本质上是一个 Handler 装饰器：输入下一个 Handler，返回一个新的 Handler。

执行方向：

```text
A 前置 → B 前置 → Handler → B 后置 → A 后置
```

因此注册顺序非常重要。最外层中间件最先收到请求，最后拿回控制权。

重点阅读：[中间件如何工作](06.01-how-middleware-works.md)

### 2. 全局中间件与路由级中间件

包裹整个 ServeMux：对所有请求生效。

```text
middleware → mux → handler
```

包裹某个具体 Handler：只对特定路由生效。

```text
mux → middleware → handler
```

典型选择：

- 全局：panic 恢复、请求日志、安全标头。
- 动态页面：会话加载、CSRF、身份识别。
- 受保护路由：授权检查。

### 3. 提前返回

中间件可以阻止请求继续向下游传播：

```go
if !authorized {
    http.Error(w, "Forbidden", http.StatusForbidden)
    return
}

next.ServeHTTP(w, r)
```

常见错误是写完拒绝响应后忘记 `return`，导致后续 Handler 仍然执行。

### 4. 横切关注点

本章实现了三个典型中间件：

- `commonHeaders`：统一添加安全响应标头。
- `logRequest`：记录 IP、协议、方法和 URI。
- `recoverPanic`：捕获同一请求 goroutine 中的 panic，记录错误并返回 `500`。

panic 恢复通常使用延迟函数：

```go
defer func() {
    if err := recover(); err != nil {
        w.Header().Set("Connection", "close")
        app.serverError(w, r, fmt.Errorf("%s", err))
    }
}()
```

注意：请求中间件不能恢复另一个后台 goroutine 中的 panic。后台 goroutine 必须自行设置 `defer`/`recover`。

### 5. 可组合中间件链

手动嵌套：

```go
return recoverPanic(logRequest(commonHeaders(mux)))
```

使用 Alice：

```go
standard := alice.New(app.recoverPanic, app.logRequest, commonHeaders)
return standard.Then(mux)
```

可以在基础链上追加中间件：

```go
dynamic := alice.New(app.sessionManager.LoadAndSave, noSurf, app.authenticate)
protected := dynamic.Append(app.requireAuthentication)
```

## 七、Chapter 10：Authentication / Authorization

原文入口：[Chapter 10 User Authentication](10.00-user-authentication.md)

### 1. 认证与授权

- 认证（Authentication）：确认“你是谁”，例如验证邮箱和密码。
- 授权（Authorization）：确认“你是否可以做这件事”，例如只有登录用户可以创建 snippet。

隐藏导航链接不是授权。用户仍可直接请求 URL，所以服务端必须执行授权检查。

### 2. 用户模型与领域错误

用户模型提供三个核心操作：

```go
Insert(name, email, password string) error
Authenticate(email, password string) (int, error)
Exists(id int) (bool, error)
```

典型领域错误：

```go
ErrInvalidCredentials
ErrDuplicateEmail
```

登录时，无论邮箱不存在还是密码错误，都返回同一个通用错误，避免暴露某个账号是否存在。

数据库的唯一约束才是阻止重复邮箱的最终保证。先查询再插入会产生检查与写入之间的竞态；应依赖唯一约束，并把数据库重复键错误转换成 `ErrDuplicateEmail`。

### 3. 密码存储

绝不存储明文密码。流程如下：

```text
注册：明文密码 → bcrypt.GenerateFromPassword → 存储哈希
登录：读取哈希 → bcrypt.CompareHashAndPassword → 判断是否匹配
```

```go
hash, err := bcrypt.GenerateFromPassword([]byte(password), 12)
err = bcrypt.CompareHashAndPassword(hash, []byte(password))
```

bcrypt cost 越高，暴力破解成本和服务端计算成本都越高，需要通过实际负载测试选择。

### 4. 注册、登录与注销流程

注册：

```text
解析表单 → 字段验证 → bcrypt 哈希 → 插入用户
→ 处理重复邮箱 → 写入 flash → 303 重定向到登录页
```

登录：

```text
解析表单 → 基础验证 → UserModel.Authenticate
→ 更新会话 ID → 写入 authenticatedUserID → 303 重定向
```

注销：

```text
更新会话 ID → 删除 authenticatedUserID → 写入 flash → 重定向
```

登录和注销时调用 `RenewToken()`，可以降低会话固定攻击风险。认证状态改变或权限升级时更新会话 ID 是重要安全习惯。

### 5. 会话与授权中间件

登录成功后，把用户 ID 放入会话：

```go
app.sessionManager.Put(r.Context(), "authenticatedUserID", id)
```

受保护路由通过中间件执行授权：

```go
func (app *application) requireAuthentication(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if !app.isAuthenticated(r) {
            http.Redirect(w, r, "/user/login", http.StatusSeeOther)
            return
        }

        w.Header().Set("Cache-Control", "no-store")
        next.ServeHTTP(w, r)
    })
}
```

`Cache-Control: no-store` 可避免受保护页面被浏览器或中间缓存保存。

### 6. CSRF 防护

CSRF 的本质：攻击者诱导已登录用户的浏览器向你的应用发送状态更改请求，浏览器可能自动携带会话 Cookie。

防护组合：

- 所有状态更改使用 `POST`、`PUT` 或 `DELETE`，不要用 `GET`。
- 会话 Cookie 设置 `Secure`、`HttpOnly` 和合适的 `SameSite`。
- 使用成熟库生成并验证 CSRF token，不要自己设计协议。
- 在所有状态更改表单中放入隐藏 token。
- 测试 token 缺失或错误时请求会被拒绝。

双重提交 Cookie 的简化流程：

```text
GET 表单
  → 服务端发送 CSRF Cookie，并在 HTML 中渲染同一 token
POST 表单
  → 浏览器发送 Cookie，表单发送隐藏 token
中间件
  → 比较二者，匹配才允许继续
```

`SameSite` 是纵深防御的一部分，不应轻率地把它当作唯一防线。

重点阅读：[用户注册](10.03-user-signup-and-password-encryption.md)、[用户登录](10.04-user-login.md)、[用户授权](10.06-user-authorization.md)、[CSRF 防护](10.07-csrf-protection.md)

## 八、Chapter 11：Request Context

原文入口：[Chapter 11 Using Request Context](11.00-using-request-context.md)

### 1. Context 的请求生命周期

每个 `http.Request` 都包含一个 `context.Context`：

```go
ctx := r.Context()
```

添加值并不是原地修改，而是创建新 Context 和新 Request：

```go
ctx := context.WithValue(r.Context(), key, value)
r = r.WithContext(ctx)
```

这两个“复制”概念必须记住：

- `context.WithValue` 返回派生 Context。
- `r.WithContext` 返回 Request 的浅副本。

### 2. 避免键冲突

不要使用普通字符串作为 Context key。不同包可能使用相同字符串，造成碰撞。

```go
type contextKey string

const isAuthenticatedContextKey = contextKey("isAuthenticated")
```

更严格的项目也可使用未导出的空结构类型作为 key。原则是：key 的类型或值应由当前包私有控制。

读取值需要类型断言，并采用安全默认值：

```go
func (app *application) isAuthenticated(r *http.Request) bool {
    authenticated, ok := r.Context().Value(isAuthenticatedContextKey).(bool)
    if !ok {
        return false
    }
    return authenticated
}
```

安全相关状态读取失败时，应“默认拒绝”，而不是默认允许。

### 3. 认证状态的请求内传递

本书使用 `authenticate` 中间件：

1. 从 Session 读取 `authenticatedUserID`。
2. 查询用户是否仍存在。
3. 若存在，将 `isAuthenticated=true` 写入 Request Context。
4. 把新 Request 传给后续 Handler。

这样做的价值：

- 一次请求只做一次用户存在性查询。
- 授权中间件、Handler 和模板数据都读取同一个结果。
- Session 中残留的用户 ID 不会自动被视为有效用户。

```go
ctx := context.WithValue(r.Context(), isAuthenticatedContextKey, true)
next.ServeHTTP(w, r.WithContext(ctx))
```

### 4. Context 的正确边界

Context 适合：

- 请求范围的身份信息。
- request ID、trace ID。
- 截止时间、取消信号。
- 请求链中多个组件都需要读取的少量元数据。

Context 不适合：

- 数据库池、记录器等应用级依赖。
- 普通函数参数的替代品。
- 跨请求持久化数据。
- 大型可变对象。
- 仅仅为了少写一个显式参数。

一句话判断：这个值是否只属于当前请求，并且需要沿调用链传播？如果不是，通常不要放入 Request Context。

重点阅读：[Context 工作方式](11.01-how-request-context-works.md)、[认证/授权 Context](11.02-request-context-for-authentication-authorization.md)

## 九、Chapter 13：Testing

原文入口：[Chapter 13 Testing](13.00-testing.md)

### 1. 测试层次

| 层次 | 测试对象 | 常用工具 | 优点 | 代价 |
| --- | --- | --- | --- | --- |
| 单元测试 | 纯函数、单个组件 | `testing.T` | 快、定位精确 | 覆盖范围小 |
| Handler/中间件测试 | 单个 HTTP 组件 | `httptest.ResponseRecorder` | 无需真实服务器 | 不验证完整路由链 |
| 端到端测试 | 路由、中间件、Handler | `httptest.NewTLSServer` | 接近真实请求 | 依赖设置更多 |
| 集成测试 | Model 与真实数据库 | 测试数据库 | 验证真实 SQL/驱动 | 慢、需要隔离数据 |

不是层次越高越好。组合使用：大量快速测试，加少量关键路径的集成/端到端测试。

### 2. 表驱动测试与子测试

```go
tests := []struct {
    name string
    input string
    want string
}{
    {name: "valid", input: "...", want: "..."},
    {name: "empty", input: "", want: ""},
}

for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) {
        got := function(tt.input)
        if got != tt.want {
            t.Errorf("got %q; want %q", got, tt.want)
        }
    })
}
```

- `t.Errorf()` 记录失败但继续当前测试。
- `t.Fatal()` 记录失败并立即停止当前测试，适合设置失败后无法继续的情况。
- 自定义断言助手应调用 `t.Helper()`，让失败位置指向调用处。

重点阅读：[单元测试和子测试](13.01-unit-testing-and-sub-tests.md)

### 3. 测试 Handler 和中间件

`httptest.ResponseRecorder` 实现了 `http.ResponseWriter`：

```go
rr := httptest.NewRecorder()
r := httptest.NewRequest(http.MethodGet, "/", nil)

handler.ServeHTTP(rr, r)
rs := rr.Result()
defer rs.Body.Close()
```

检查状态码、标头和响应体。测试中间件时，传入一个简单的 `next` Handler，并同时断言：

- 中间件产生了预期副作用。
- `next` 确实被调用，或在应拦截时没有被调用。

重点阅读：[测试 HTTP Handler 和中间件](13.02-testing-http-handlers-and-middleware.md)

### 4. 端到端测试

```go
ts := httptest.NewTLSServer(app.routes())
defer ts.Close()

rs, err := ts.Client().Get(ts.URL + "/ping")
```

关键点：

- 把 `app.routes()` 交给测试服务器，真实路由和中间件都会执行。
- TLS 测试必须使用 `ts.Client()`，它已信任测试服务器证书。
- 使用 Cookie Jar 保存跨请求 Cookie。
- 禁止自动跟随重定向，才能断言原始 `3xx` 响应和 `Location` 标头。

```go
ts.Client().CheckRedirect = func(req *http.Request, via []*http.Request) error {
    return http.ErrUseLastResponse
}
```

### 5. 模拟依赖与接口

如果 `application` 字段是具体类型，就无法轻易替换为模拟对象。把依赖定义为消费者需要的最小接口：

```go
type SnippetModelInterface interface {
    Insert(title, content string, expires int) (int, error)
    Get(id int) (Snippet, error)
    Latest() ([]Snippet, error)
}
```

生产 Model 和模拟 Model 只要实现相同方法，就都能注入应用。

重要设计原则：接口应围绕使用方的需要定义，不要为了“可能有一天需要”而创建巨大接口。

模拟适合验证 Handler 如何处理：成功、记录不存在、重复邮箱、凭据错误等分支。它不能证明真实 SQL 正确，因此还需要集成测试。

### 6. 测试带 CSRF 的表单

模拟真实浏览器工作流：

1. `GET` 表单页面，获得 CSRF Cookie 和页面 token。
2. 从 HTML 中提取并反转义 token。
3. 用同一个带 Cookie Jar 的客户端提交 `POST`。
4. 把 token 和其他表单字段一起发送。
5. 分别测试有效 token、无效 token 和各类字段错误。

这是一个重要思想：安全机制使测试稍复杂是正常的，不要为了让测试方便而在测试环境绕过安全中间件。

### 7. 数据库集成测试

测试数据库应与生产数据库分离。每个测试建立已知状态，并在结束后清理：

```go
func newTestDB(t *testing.T) *sql.DB {
    db := ...
    // 执行 setup.sql

    t.Cleanup(func() {
        // 执行 teardown.sql
        db.Close()
    })

    return db
}
```

每个子测试独立 setup/teardown，可以避免测试间状态泄漏。不要并行运行会操作同一数据库状态的集成测试。

慢测试可以这样跳过：

```go
if testing.Short() {
    t.Skip("skipping integration test")
}
```

### 8. 常用命令

```bash
# 所有测试
go test ./...

# 详细输出
go test -v ./...

# 运行指定测试/子测试
go test -run='^TestName$/^CaseName$' ./...

# 禁用缓存
go test -count=1 ./...

# 快速模式，供测试代码通过 testing.Short() 判断
go test -short ./...

# 竞态检测
go test -race ./...

# 覆盖率
go test -cover ./...
go test -coverprofile=/tmp/cover.out ./...
go tool cover -html=/tmp/cover.out
```

覆盖率回答“哪些语句执行过”，不回答“测试断言是否正确”或“关键场景是否覆盖”。不要把百分比当成唯一目标。

## 十、贯穿七章的关键关系

### 1. `http.Handler` 是组合中心

ServeMux、应用 Handler、中间件和测试服务器都围绕 `http.Handler` 组合。这是本书最重要的接口。

### 2. 依赖注入连接生产代码与测试

```text
main 创建真实依赖 → application → Handler
测试创建模拟依赖 → application → 同一个 Handler
```

如果没有第 3 章的依赖注入，第 13 章的模拟测试会困难得多。

### 3. Model 隔离数据库细节

```text
sql.ErrNoRows → Model 转换 → models.ErrNoRecord → Handler 转换 → HTTP 404
```

每一层只处理自己理解的错误语言。

### 4. Middleware 与 Context 配合

Middleware 在请求进入 Handler 前计算通用信息，Context 把计算结果沿当前请求向下传递。

```text
authenticate 中间件
  → 查询用户是否存在
  → Context 写入认证状态
  → requireAuthentication / Handler / 模板读取
```

### 5. 安全依赖多层防御

```text
密码哈希
+ 唯一约束
+ Session ID 更新
+ Secure/HttpOnly/SameSite Cookie
+ CSRF token
+ 服务端授权中间件
+ Cache-Control: no-store
```

任何单独一层都不能替代其他层。
